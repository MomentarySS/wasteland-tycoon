## 0. 结论先行

**方向可行，但「重制」的落点不是换引擎。**

推荐路线：**保留规则层 / 存档层 / TTS 层不动，重制渲染层与视觉资产层**，具体为
「Canvas 三层分离 + 脏标记渲染 + 程序化材质 + 视觉一致性重建」，这是一次**中等强度、可分阶段、可验收**的重制。

> **2026-11-12 决策更新（Q1–Q3 已定）**：画质形态 = **废土终端 HUD 精致化**（仍 2D，不换引擎）；
> **暂不投入插画美术**，原「44 张地块插画重制」移出范围，M3 降级为程序化材质；
> 硬件基线 = 核显起步 + 独显典型。下文 2.1 / 2.3 / M3 / 工时汇总已同步。

明确**不推荐**的三条路：

| 路线 | 判断 | 理由 |
|---|---|---|
| 换 WebGL 引擎（PixiJS / Three.js / 自写 WebGL） | ❌ 不推荐 | 本作可视对象约 200 个（44 棋格 + 4 棋子 + 少量特效），WebGL 的收益在海量精灵 / 3D / 全屏后处理才显现；本作已有 DOM UI（侧栏、弹窗、战报、TTS 调试），换引擎后 UI 仍需 DOM，收益被对半砍；且会打断刚完成四批修复的规则 / 存档 / 安全链路 |
| 推倒重写整个项目 | ❌ 不推荐 | `game.js` 41KB / `view-core.js` 29KB / `tts.js` 22KB 的复杂度里有大量已经过审查、变异校验的规则语义，重写等于重做全部安全审查 |
| 在现有版本上纯打补丁式优化 | ⚠️ 部分可行 | 但存在**收益天花板**：当前架构是「任何状态变化 → 全量重绘 44 格」，无论怎么微调，单次全绘的成本量级（每帧 44 格 × 渐变 + 文本测量）下不来。视觉升级又会持续引入新的每帧绘制 |

> **核心判断**：本项目的画质天花板不在「能不能用 WebGL」，而在 **① 美术资产质量 ② 光照模型一致性 ③ 渲染架构是否支持分层合成**。
> （2026-11-12 注：Q2 决定暂不投入插画，**① 的天花板被锁死**，提升主要靠 ②③ 与程序化材质。）
> 前两项是资产与设计投入，第三项是必须先做的地基 —— 没有分层合成，就无法做真正的发光混合、Bloom、暗角、颗粒这些"合成式"效果，只能继续叠 DOM/CSS 图层。

### 1.2 渲染与更新逻辑（**这是理解全局最关键的一节**）

**棋盘画在 Canvas 上，但不是逐帧引擎，而是事件驱动的全量重绘。**

```
状态变化（买地 / 升级 / 缴租 / 结算…）
   └─ rules.js / game.js 约 20 处调用点
        └─ view-core.js render()
             ├─ fitBoard()          ← 4~6 次布局读取 + 13 个 CSS 变量写入
             ├─ resizeBoardCanvas() ← 无条件写 canvas.width/height（位图重分配）
             ├─ drawBoard()         ← rAF 合帧，全量 renderAll()
             ├─ renderPlayers()     ← innerHTML 重建玩家面板 + 地产缩略条
             ├─ repositionAllTokens()
             └─ markMonopolyTiles() ← 内部又触发一次 drawBoard()  ★ 画两遍
```

**格子绘制单元（`drawTile`）每次做**：底色填充 → 贴图 cover 裁切 → 2 个 `createLinearGradient` → 区域纹理叠加 → 内壁高光/底部内阴影 → 顶边色条 → 描边 → 名称排版（二分字号 + 逐字 `measureText`）→ 角标 SVG → HUD（等级徽章 / 建造图标 / 产权色点 / 辉光）。

**没有常驻 rAF 主循环。** 唯一的持续帧循环是 `tickTilePulse`（脉冲动画期间每帧 `renderAll()`）与 `moveTokenAnim` 的逐格移动（每步 `await rAF` + `sleep(150)`）。回合流程是**串行 async 单链**（`takeTurn`），每步固定等待 150ms，一回合动辄数秒，期间 Canvas 完全静止，只剩 DOM 动画在跑。

**文本与特效是 DOM 的**：地块名由 Canvas 绘制（等宽 `Courier New`），侧栏/弹窗/战报/棋子/飘字全是 DOM + WAAPI 动画，FX 层节点上限 120。

### 1.3 瓶颈定位（已确认事实 vs 待实测）

> 区分说明：标 ✅ 的是从代码可直接确认的事实；标 ⚠️ 的是静态推算，必须实测验证后才能作为优化依据。

| # | 位置 | 问题 | 性质 |

| D3 ✅ | `icons.js` / `assets-art.js` | `tileIcon()` 每次调用**重建 20 项 SVG 对象字面量**；`svgCache` 的 key 是 `color + '|' + 完整 SVG 字符串`（Map key 巨大、哈希成本高）；`tileArtUrl()` 每帧构造 URL 字符串 | 性能 + GC |
| D4 ✅ | `board-metrics.js:32-48` | `getTileRect()` 每次 `querySelector` + `getBoundingClientRect()`，且与样式写入**交错**（移动循环里先写样式再读布局）→ 强制回流 | 性能 |

| D7 ✅ | `view-core.js:407-430` | 战报 DOM 上限 100 条，每条追加后 `rAF` 加 `.in` 触发入场动画 → 长局 DOM 持续增长 | 内存 |
| D8 ✅ | `game.js:65-93` | 每步移动固定 `sleep(150)`，逻辑与动画**串行绑定** → 回合耗时 = 步数 × 150ms 线性累加 | 体感流畅度 |

| D10 ⚠️ | 全局 | **无任何 FPS / 帧时间 / 内存埋点**。以上所有结论目前只能靠静态推算 —— **这是重制前必须先补的短板** | **最高优先级前置项** |

**已验证无问题项**（避免重制时误伤）：

- ✅ 存档层与渲染层**完全解耦**：存档只写 `G` 的规则字段 + `TILES(owner/level/mortgaged/price)` + `boardArtOrder` + `players`，**不含任何渲染状态**。`view-save.js` 已有 `normalizeSave()` + `validateSave()` 白名单收敛（`SAVE_VERSION = 4`）。
- ✅ 已有 `prefers-reduced-motion` 降级路径、`page-hidden` 前后台暂停、FX 节点上限、DOM 降级渲染路径（`#tiles`）。
- ✅ `board-canvas.js` 的 Canvas / DOM 双路径结构本身就是「可分层重制」的良好地基。

### 1.4 存档兼容的硬约束（重制全程必须守住）

| 约束 | 说明 |
|---|---|
| `G` 对象是唯一事实源 | 规则层写、渲染层只读。**重制不得把渲染状态写进 `G` 或 `TILES`** |
| `SAVE_VERSION = 4` 不变 | `view-save.js:13-14`；`normalizeSave` 继续做白名单收敛，新增字段一律拒收 |
| `boardArtOrder` ↔ `content/tiles.json` 地块顺序 | 若重制改动地块数据或顺序，存档里的布局映射会错位（历史已踩过，见 `code-review-2026-11-12.md` C8） |
| `TILES` 数组结构 | `id / type / group / price / artIndex / name / owner / level / mortgaged`，重绘资产**不能**改变 `artIndex` 语义 |
| DOM 降级路径 | `dom-stub` 冒烟测试依赖无 DOM 环境降级不报错，重制后仍须通过 `npm test` |
| 画质偏好 | 若新增「画质档位 / UI 缩放」，**独立存 `wasteland_prefs`**，绝不混入 `wasteland_save`，避免存档 schema 变更 |

### 2.2 P0：渲染分层重构（画面与性能的地基）

**问题**：现在是「一个 canvas 全量重绘」。要做真正的发光混合、Bloom、暗角，必须先有**层**。

**目标结构**：

```
┌─ #canvasStatic  离屏烘焙，仅当「布局 / 地块内容 / 尺寸」变化时重绘
│    └─ 底色 + 地块贴图 + 材质噪点 + 区域纹理 + AO 内阴影 + 顶边色条
├─ #canvasBoard   每帧按需重绘（脏标记驱动）
│    └─ 名称文本(缓存) + 角标 + HUD + 产权色条 + 垄断/当前/悬停光效
├─ #canvasFx      粒子 + 脉冲 + 扫描 + 加法混合发光
└─ DOM 层（保留）  棋子 / 飘字 / 侧栏 / 弹窗 / 战报 / 摇骰
```

**收益**：静态层烘焙一次 → 后续每帧只需重绘「变化的格子」；Bloom 可以只对 FX 层做降采样合成；DOM UI 完全不受影响。

**取舍**：多一层 canvas = 多一次 `drawImage` 全屏合成（约 0.3–0.8ms @1800×1500），但换掉的是每帧 44 格全绘（实测需验证，预计 4–10ms）。**净收益需实测确认**，不能拍脑袋。

### 2.3 ~~P0：地块插画纵横比重制~~（**已移出范围**，2026-11-12）

> **Q2 决策：暂不投入插画美术。** 本节方案保留为「日后重启美术时的依据」，当前不执行。
> M3 以程序化材质替代（见 M3 章节）。现有 512×256 插画保持不动，`artIndex` 映射不变，存档零影响。

**现状硬伤（已确认）**：地块插画源图 **512×256 = 2:1**，而棋盘格子在常见 16:9 窗口下约 **72×60 = 1.2:1**（`fitBoard()` 独立算宽高，不锁比例）。`drawCover()` 按 cover 裁切 → **每张图约 40% 的宽度被裁掉**，插画本该有的构图（主体位置、留白）大概率没按 1.2:1 设计。

**方案**：把 44 张地块插画重制为 **1:1 或 1.25:1 构图**（与实际格子接近），同时提供 2x 尺寸（1024×1024 或 1024×1280）用于高 DPR。

- 收益：**单格观感提升是结构性的**（不是滤镜能补的），且这是当前唯一「素材本身不够好」的硬伤
- 成本：44 张重绘 + 筛选用（项目已有 `sharp` / `@resvg/resvg-js` 工具链，AI 生图 + 脚本批处理可行）
- 兼容：`artIndex` 映射不变，只换文件 → **不影响任何存档**

### 2.4 P0：统一光照模型（把「贴纸拼贴」变成「有体积的实物」）

**现状**：格子只有固定顶部 3px 色条 + 底部内阴影 + 单向线性渐变压暗。四面格子亮度一致 → 看起来像贴图拼贴，没有厚度。

**方案**：

1. **主光源固定左上 315°**。格子四边按朝向给不同高光强度：顶/左边提亮（`rgba(255,255,255,.10)`），底/右边压暗（`rgba(0,0,0,.28)`），让每格读起来是一块有厚度的板。
2. **接触阴影（AO）**：格子之间加 1–2px 的 `rgba(0,0,0,.35)` 内阴影 + 外投影，棋盘立刻有实体感。
3. **高度场**：让所有格子保持同一光照方向 —— 包括侧栏的地产缩略条、HUD 徽章、事件插画边框。
4. **全局光照随天气 / 时段变化**：沙尘 = 暖色低对比 + 雾；酸雨 = 冷青 + 雨痕；辐射 = 绿荧光；黄昏 = 长投影。项目已有 `body.weather-*` class 和 R1–R4 背景变体，接入成本低。

**成本**：主要工作在绘制代码（静态层烘焙阶段），一次性。

### 2.5 P1：Canvas 粒子系统与真正的发光混合

**现状**：粒子是 DOM `div` + WAAPI（`fx-events.js` 的 `ART_MOTES` 每事件 3–8 个），加法混合做不到（DOM 只能 `mix-blend-mode`，受层叠上下文限制，且每个节点独立合成）。

**方案**：把粒子系统整体迁到 `#canvasFx`：

- 粒子池化：预分配 512–1024 个粒子对象，**零 GC 分配**
- 支持加速度 / 阻尼 / 噪声场 / 拖尾
- 混合模式：`globalCompositeOperation = 'lighter'`（加法）→ 真正的发光
- 与 Bloom 配合：FX 层单独降采样（1/4）→ `ctx.filter = 'blur()'` → 加法叠回

**收益**：这是「DOM 特效 → 电影感」的分界线。占领协议的扫描线、LOCKED 标记、垄断辉光都能从「描边」升级为「发光」。

### 2.6 P1：全屏后处理（Bloom / 暗角 / 颗粒 / 扫描线）

**现状**：是「贴纸式」的 —— CSS 背景图 + `mix-blend-mode` 叠层，不是合成式。

**方案**（离屏 canvas 链）：

```
#canvasFx (加法发光)  ──┐
                        ├─→ 1/4 降采样 → blur → 加法叠回 → 暗角 → 颗粒 → 扫描线
#canvasStatic          ─┘
```

- **Bloom**：只对 FX 层做，避免静态图整体泛光糊掉
- **暗角（vignette）**：一张程序化径向渐变，`multiply` 混合，比全屏 CSS 图层更省
- **颗粒（grain）**：程序化噪声纹理（一张 256×256 循环贴图），比 CSS 图层便宜，且能加「胶片感」
- **扫描线**：低透明度水平线 pattern，`multiply`

**成本**：后处理链每帧 1–2 次全屏 pass，需实测是否掉帧；若掉帧，做成**画质档位开关**（高 / 中 / 低）。

### 2.7 P2：UI 视觉与 Design Token

**现状问题**：

- 色值**双份维护**：CSS 里 `:root` 定义一次，`board-canvas.js:16-27` 的 `VAR_COLORS` / `WALL_COLORS` 又手抄一份字面量（`#b5651d` / `#c9a227`…）。已经出现漂移风险 —— canvas 侧不读 CSS 变量（canvas 解析不了 `var()`），这是历史遗留的必然。
- `style.css` 64KB 硬编码色值散落，`playerPulse` 之类动画直接动 `border-color` / `box-shadow`（非合成器属性）。

**方案**：

1. **单一事实源**：新建 `js/theme.js` 导出全部 token（色 / 间距 / 字号 / 圆角 / 阴影），CSS 侧由构建脚本或运行时注入 `:root` 变量，Canvas 侧直接 import。**一次性消除双份维护**。
2. **侧栏 / 弹窗重做**：统一卡片材质、层级阴影、标题排版、按钮四态（hover / active / disabled / focus-visible）、战报条目色彩分级。
3. **字体栈**：当前地块名用 `"Courier New", Consolas, monospace`，中文在 5–11px 下发虚、字重不匀。改为 `ui-monospace, "Cascadia Mono", Consolas, "Microsoft YaHei UI", monospace` 并提高最小字号下限（可读性优先于「像素风」）。
4. **动画属性白名单**：所有 `@keyframes` 只允许动 `transform` / `opacity`；`background-position` / `box-shadow` / `border-color` 改为等价方案或降级为静态。

### 2.8 P2/P3：分辨率与缩放方案

**问题**：目前 `fitBoard()` 独立算格子宽高，**不锁比例**；Canvas 已按 `devicePixelRatio` 适配（DPR2 时位图 1800×1500），但 DOM UI 层没有任何缩放机制，4K 下 UI 会显得小而糊。

**方案（三档缩放）**：

| 档位 | 行为 | 适用 |
|---|---|---|
| **紧凑** | 格子数不变，缩小 cell，UI 缩放 0.85 | 1080p / 小屏 |
| **标准** | 现状 | 默认 |
| **放大** | UI 缩放 1.15–1.30，格子物理尺寸增大，**位图按 DPR 重新采样**（不是拉伸） | 4K / 视力需求 |

关键：**放大档必须让 Canvas 位图按新 DPR 重新分配**，而不是 CSS 拉伸（否则模糊）。`resizeBoardCanvas()` 本来就有 DPR 逻辑，只需去掉「无条件重分配」并加上档位驱动。

另需处理：超宽（>21:9）、竖长屏、4K、150%/200% 系统缩放、多显示器不同 DPI。`fitBoard()` 已有 21:9 / 竖屏分支，可扩展。

## 3. 流畅度：瓶颈定位思路与优化措施

### 3.1 第一步：先建基线（**不可跳过**）

> 项目当前**没有任何性能埋点**（D10）。没有基线的优化全是猜测 —— `visual-effects-plan.md` 里那次「渐变 memo A/B 实测 SPLIT → 决定不提交」正是好范例：宁可放弃一项改动，也不留无证据的优化。

**M0 阶段必须交付**：

1. **`scripts/perf-probe.mjs`**：在真实 Electron 渲染进程内跑，记录
   - 单次 `renderAll()` 耗时（冷 / 热）
   - 一次完整脉冲（37 帧）的总耗时与 P95 帧时间
   - `render()` 端到端耗时（`fitBoard` + 位图重分配 + 两遍全绘）
   - JS heap 峰值 / DOM 节点数 / FX 层节点数
2. **Chrome DevTools Performance trace 自动录制**（`--trace-startup` 或 DevTools Protocol），产出可对比的 CPU 火焰图与 FPS 曲线
3. **回归口径固定为三档**：1080p @100%（主流）/ 1080p @200% DPI（高分屏）/ 4K @150%（顶配）

**验收基线（✅ 2026-11-17 M0 已实测回填，详见 `docs/perf-baseline.md`）**：

| 指标 | 目标 | 实测（1080p@100% / @200% / 4K@150%） | 结论 |
|---|---|---|---|
| 静态待机帧时间 | ≤ 4ms（无重绘时不应有绘制） | **0 帧**（三档一致） | ✅ 通过 |
| 单次 `renderAll()` | ≤ 3ms | canvas 操作 P50 1.1–1.8ms，P95 1.9–3.0ms | ✅ 通过（4K 贴边） |

| 回合峰值内存 | 30 分钟对局无持续增长 | 5 回合恒定 9.5MB | ⚠️ 部分验证（未跑满 30 分钟） |

> **本机实测刷新率 163.9Hz**（帧预算 6.1ms，不是 16.7ms）。4K 档脉冲 rAF 回调 P95 5.5ms，
> 在高刷机型上已逼近预算，M6 缩放方案需要把这个余量考虑进去。

> **两条静态推算被实测修正**：
> - **D1「每轮画两遍」不成立** —— `drawBoard()` 的 rAF 合帧已合并同帧调用，实测全板重绘 2–3 次。
>   真正该修的是 `resizeBoardCanvas` 的**无条件位图重分配**（每次 render 分配 6 / 22.5 / 61.3 MB）。
> - **D2 的总量口径要按实际刷新率重算** —— 每帧 868 次 `measureText`、88 个渐变与推算吻合，
>   但 620ms 脉冲在 164Hz 下是 76–100 帧，总 `measureText` 7.0–8.0 万次，不是 4.4 万。

### 3.3 帧率稳定方案

1. **单一调度器**：把 `drawBoard()` 的 rAF 合帧机制升级为**全局帧调度器** —— 所有绘制请求（静态失效 / 动态脏格 / 粒子 / 后处理）在同一帧内合并，按层顺序执行一次。
2. **动画预算**：同一时刻活跃粒子 / WAAPI 动画总数设上限（现有 FX 层 120 上限是 DOM 版的，粒子版按 GPU 填充率另设）。超预算时优先丢弃装饰粒子，保留结果标签（沿用现有 `trimFxLayer` 的淘汰优先级语义）。
3. **降级链**：`prefers-reduced-motion` → 关闭粒子/扫描/Bloom 保留静态语义 → 保留颜色/标签/边框（沿用现有约定，扩到新效果）。再降一档：低画质档关闭 Bloom 与颗粒。
4. **后处理自适应**：若实测 Bloom 使帧时间超阈值，自动降为「单次降采样 + 轻模糊」或关闭（运行时自适应的画质旋钮）。
5. **可观测**：新增开发态 FPS / 帧时间叠加层（`F3` 切换），线上不暴露。

## 5. 「重制」vs「在现有版本上迭代」

| 维度 | 重制（重做渲染层 + 视觉层） | 迭代（在现有架构上打补丁） |
|---|---|---|
| **画面上限** | 高。可实现加法发光、Bloom、颗粒、方向光 —— 这些**要求分层合成**，现有单层 canvas 结构做不到 | 中。多层 DOM/CSS 叠加能做出「风格化」效果，但做不出「电影感」，且 DOM 层数越多合成越贵 |
| **性能上限** | 高。分层 + 脏标记是唯一能把「每帧 44 格全绘」降下来的结构性方案 | 低。D1/D2 的量级（每帧全绘 + 4 万次 measureText）只能微调，压不到帧时间预算内 |
| **风险** | 中高。动的是渲染主干 + 视觉资产 | 低。改动局部，回滚容易 |
| **存档兼容** | 可控（重制层与存档层解耦，红线 R1–R7） | 天然兼容 |
| **规则风险** | 可控（规则层冻结，红线 R6） | 天然兼容 |
| **工期** | 34–53 人天 | 零散优化约 8–12 人天可拿 30–50% 的帧时间改善 |
| **可维护性** | 高。三层结构 + token 单一源 + 脏标记，后续加效果是「加一层」不是「改全局」 | 低。`game.js` 846 行 / 8 类职责、`view-core.js` 25 个导出混 7 类职责、循环依赖 `rules.js → view.js ↔ game.js`，每加一个视觉特性都在这堆耦合上加负担 |
| **技术债** | 顺带清掉 M2/M5 里的重复实现与死代码 | 继续累积（`sleep` 三份、`escapeHtml` 两份、已验证死代码若干） |

### 推荐结论

**推荐「有限范围的重制」**，边界如下：

**做**：
1. 渲染层重制（M1 + M2）—— 这是性能与画质的共同地基，不可省
2. 视觉光照与材质（M3，**程序化材质，不含插画重制**）—— 仍是画质天花板之一，但上限因不投入美术而降低
3. UI 设计系统（M5 的 token 部分）—— 消除双份维护是低成本高回报
4. 分辨率/缩放方案（M6）—— 4K 是当下真实需求

**不做**：
1. ✗ 不换渲染引擎（PixiJS / Three.js）
2. ✗ 不重写规则层、存档层、TTS 层
3. ✗ 不动 Electron 安全模型（`contextIsolation` / `sandbox` / CSP / IPC 来源校验已过审）
4. ✗ 不改玩法、数值、事件文案
5. ✗ 不引入打包器 / TypeScript（保持零构建，除非你明确要改）

**理由（简述）**：本项目真正的画质瓶颈是**资产质量 + 光照一致性 + 分层合成能力**，不是渲染 API 的先进程度。而真正的性能瓶颈是**架构层面的每帧全量重绘**，也不是 API 决定的。换引擎解决不了这两个问题，却会引入新的风险面和工具链复杂度。

**~~但先做这个决策~~ → 已确认（2026-11-12）**：保持 2D Canvas + DOM HUD，走「废土终端 HUD 精致化」，**不转 3D / 写实**。若日后真实诉求变为 3D / 电影级质感，需重新讨论美术方向与技术路线，而不是在 2D Canvas 上加后处理。

### C2 手机端布局三方向

| 方向 | 布局 | 适配性 | 风险 |

| C. 竖向环形压缩 | 保留环形但纵向拉长，顶部/底部收窄 | 折中方案 | 格子变小、文字可读性风险高 |
